Серверный конфиг [Xray](https://github.com/XTLS/Xray-core) для создания туннеля, который **подменяет DNS-резолвинг** на стороне клиента, заставляя все DNS-запросы идти через `77.88.8.8` (Яндекс.DNS), скрывая реальные домены от провайдера. Трафик маскируется под обычный HTTPS-сеанс к `amd.com`.

---

## ✨ Особенности

- 🎯 **Порт 13868** – высокий порт, редко блокируемый DPI.
- 🧠 **REALITY** – использует TLS-сертификат сайта `amd.com`; при пассивном анализе выглядит как легитимное соединение с AMD.
- 🔒 **TCP + REALITY** – надёжная обёртка зашифрованного VLESS-трафика в TLS с реальным сертификатом.
- 🧩 **finalmask xdns** – принудительная замена всех DNS-запросов на `77.88.8.8` (Яндекс.DNS) в рамках туннеля; ни один запрос имени не уходит на DNS провайдера.
- 🕵️ **FakeDNS** – внутренний DNS-сервер Xray, который вместе с xdns исключает любые утечки имён.
- 🚫 **Блокировка торрентов** – правило в routing отсекает P2P-трафик.
- ⏱️ **Политика таймаутов** – приближена к поведению реального браузера.

---

## 🔍 Принцип маскировки (что видит DPI)

1. **SYN → SYN‑ACK → ACK** – стандартное TCP-рукопожатие на порт 13868.
2. **Клиент отправляет TLS Client Hello** – с SNI `amd.com` и fingerprint обычного браузера (зависит от клиента).
3. **Сервер отвечает Server Hello** – REALITY подставляет настоящий сертификат `amd.com`, полученный от целевого сайта.
4. **Весь дальнейший обмен** – это зашифрованный VLESS-трафик, упакованный в обычные TLS-пакеты (без дополнительных HTTP-заголовков, как в xHTTP). Для DPI это выглядит как обычный HTTPS-сеанс пользователя, зашедшего на `amd.com`.

Дополнительно:
- **finalmask xdns** на стороне сервера передаёт клиенту директиву использовать `77.88.8.8` для всех DNS-запросов. Клиент (совместимый) будет резолвить домены через этот внешний DNS, но все запросы останутся внутри TLS-туннеля.
- Никакие DNS-пакеты не покидают туннель наружу – провайдер видит только TCP-пакеты на `13868` с внешними признаками TLS-сессии к `amd.com`.

---

## ⚙️ Когда использовать

- Если ваш провайдер или DPI пытается перехватывать/подменять DNS-ответы.
- Если нужно жёстко зафиксировать резолвинг через определённый DNS-сервер (например, Яндекс или Google).
- Когда требуется минимизировать метаданные (без UDP-шума и HTTP/2-фреймов) – более лёгкий вариант по сравнению с xHTTP.

> **Примечание:** Для поддержки `finalmask xdns` необходим клиент Xray с версией не ниже 1.8.0 (или форк с поддержкой этой директивы). Стандартные клиенты могут проигнорировать эту секцию.
